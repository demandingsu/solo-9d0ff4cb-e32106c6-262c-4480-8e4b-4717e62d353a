# 环境监测小时观测数据平台

FastAPI + SQLite 的网页应用：测站结构（列名/列型）随时间演化，旧批次观测数据
仍可按**现役列名**统一查询，也可切回**历史版本**查看当时的列名与原始读数。

在原始列之上还可以发布**计算列**（每列一次加/减/乘/除），计算口径同样版本化：
同一批读数可按新旧口径各算一遍，复算旧口径时整条依赖链用当时的口径。

## 功能

- **发布初版结构**：自定义站号列、UTC 小时列与数据列（整数 / 小数 / 文本）。
- **按现役结构上传 CSV**：表头须与现役结构一致（顺序不限），逐行校验类型，
  任何一行不合格则**整批拒绝**，不产生半成品批次。
- **结构演化（发布新版本）**，只允许三类安全变更：
  - 改列名（含站号/小时列，跨多版连续改名也能找回旧值）；
  - 新增**可空**列（旧批次该行显示空值）；
  - 整数列**扩型**为小数列（旧值原样保留，不做任何换算）。
- **拒绝并回滚**：删除旧列、两列合并、一列拆多列、缩型（小数→整数等）、
  改系统列类型、新增非空列、列名重复——全部拒绝，现役版本与供数不受影响。
- **计算列**：`左操作数 运算 右操作数`，每个计算列只做一次加、减、乘或除；
  左右操作数都可以是常量、原始列（按稳定 `column_id` 取数）或其他计算列。
- **口径版本化**：每个结构版本记录一份“每个计算列用哪版口径”的快照。
  发布新口径时，直接或间接引用它的计算列自动升版（公式不变、绑定到新上游），
  无关计算列沿用原口径；旧口径可随时整链复算。
- **拒绝无效引用与成环**：引用不存在的原始列 / 计算列、同批自环、间接成环，
  发布整体拒绝，不写入版本、口径或快照。
- **统一查询**：按站号 + UTC 小时区间查询，所有批次用现役列名展示；
  可自选计算列与口径版本，查看每条观测的计算结果、依赖口径与来源批次；
  缺值与除零给出具体原因。
- **历史视角**：选择任一历史版本，只看该版批次，列名与读数都是当时的样子。
- **交错安全**：发布 / 上传 / 查询均在全局锁 + 单事务内完成，结构与数据不混用；
  查询只读到完整的已提交口径。

## 快速开始（Docker Compose）

```bash
docker compose up --build
# 打开 http://localhost:8000
```

数据保存在命名卷 `obs-data` 中（容器内 `/srv/data/obs.db`）。

## 本地开发

```bash
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload
# 打开 http://127.0.0.1:8000
```

## 页面操作流程（可用 examples/ 下的样例 CSV）

1. 「② 发布结构版本」发布初版：站号=`站号`，小时=`UTC小时`，数据列 `气温`(整数)、`气压`(整数)。
2. 「④ 上传」选择 `examples/v1_初版结构.csv`。
3. 「②」把 `气温` 改名为 `气温_C`、`站号` 改名为 `station_code`、`气压` 扩型为小数 → 发布 v2；上传 `examples/v2_改名扩型后.csv`。
4. 「②」把 `气温_C` 改名为 `温度`，新增可空列 `湿度`(整数) → 发布 v3；上传 `examples/v3_再加列后.csv`。
5. 「③ 计算列与口径」新增 `温差 = 温度 - 气压`、`温差翻倍 = 温差 * 2`、
   `除以气压 = 温度 / 气压`，发布 v4。
6. 勾选「温差」的「发布新口径」，改成 `气压 - 温度` 发布 v5：
   「温差翻倍」自动升到第 2 版，「除以气压」仍是第 1 版。
7. 「⑤ 查询」：
   - 现役口径：温差按 v5 口径，温差翻倍随新上游；
   - 把「计算口径」切到 v4：同一批读数按旧口径各算一遍（-1008 / -2016）；
   - 「批次视角」切到 v1：列名是当时的 `站号/气温/气压`。
8. 空读数会显示「缺值：原始列…无读数」，除数为 0 会显示「除零」，并沿依赖链说明来源。

## API 一览

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/versions` | 全部版本（含原始列与该版计算列口径） |
| GET | `/api/versions/current` | 现役版本 |
| GET | `/api/versions/{no}` | 指定版本 |
| POST | `/api/versions` | 发布新版本（初版/演化/计算列），非法变更 400 |
| GET | `/api/computed-columns` | 全部计算列及其口径历史 |
| POST | `/api/batches` | 上传 CSV（multipart，字段名 `file`），校验失败 400 且整批回滚 |
| GET | `/api/batches` | 批次列表 |
| GET | `/api/observations` | 查询：`station`、`hour_from`、`hour_to`、`version_no`（批次视角）、`def_version_no`（计算口径版本）、`computed_ids`（逗号分隔）、`limit` |

发布新版本请求体示例（原始列演化 + 计算列）：

```json
{
  "note": "改名+扩型+加列+计算列",
  "columns": [
    {"source": "station", "name": "station_code"},
    {"source": "hour_utc", "name": "UTC小时"},
    {"source": "c1", "name": "温度"},
    {"source": "c2", "name": "气压", "type": "float"},
    {"source": null, "name": "湿度", "type": "integer", "nullable": true}
  ],
  "computed_columns": [
    {"name": "温差", "key": "diff", "op": "-",
     "left": {"kind": "column", "ref": "c1"},
     "right": {"kind": "column", "ref": "c2"}},
    {"name": "温差翻倍", "op": "*",
     "left": {"kind": "computed", "ref": "diff"},
     "right": {"kind": "const", "value": 2}},
    {"column_id": "d9", "op": "+",
     "left": {"kind": "column", "ref": "c1"},
     "right": {"kind": "const", "value": 1}}
  ]
}
```

- 新计算列：给 `name`，可选 `key`（供同一请求里的其他新列引用）。
- 现役计算列发布新口径：给 `column_id` + `op/left/right`；只沿用则不要列出。
- `kind=column` 的 `ref` 是稳定 `column_id`（也接受本版列名，发布时解析为标识）；
  `kind=computed` 的 `ref` 是 `computed_id` / 现役名称 / 本批新列的 `key` 或名称。
- 初版用 `{"role": "station"/"hour"/"data", "name": ..., "type": ...}` 声明列。

## 设计说明

- **列血缘**：每个逻辑列有稳定标识 `column_id`（`station` / `hour_utc` / `c1` / `c2` …）。
  改名、扩型复用同一 `column_id`，因此改名链跨多版仍可定位旧值。
  计算列另有稳定标识 `computed_id`（`d1` / `d2` …），公式按标识取数，
  原始列改名或扩型都不会让公式失配。
- **原值存储**：观测值按上传时的解析结果存入 `observations.values_json`
  （`{column_id: value}`），之后任何版本操作都不改写它。新增列在旧行自然为空；
  扩型不回填（旧整数仍是整数，数值不变）。计算列不入 CSV、不落库，
  总是在查询时按所选口径实时求值。
- **口径不可变 + 快照**：`computed_definitions` 每次新定义只追加 `def_no`；
  `schema_version_computed` 记录每个结构版本使用哪条定义。复算旧版本时，
  依赖链中的每一环都取该快照的定义，因此“旧口径复算”是整链的，不会混入新口径。
- **间接升版**：发布新定义时，在现役依赖图上找出所有直接/间接依赖者，
  自动为它们复制一条新定义（公式不变，`computed` 引用仍指向稳定标识，
  求值时经快照解析到新上游）；无关计算列沿用原定义。
- **发布原子性**：计算列引用、成环、名称冲突全部在写库前校验；
  之后才在单事务里写版本、原始列、口径与快照。失败整体回滚，
  失败操作前已提交的口径不受影响。
- **事务与锁**：所有读写经 `db.session()`（全局 RLock + 单连接事务）。
  发布/上传先完整校验再写入，失败整体回滚——失败操作后仍按原版本供数。
  快照与观测在同一次读取/事务中取得，查询不会看到半套口径。
- **小时规范化**：`2026-11-18 03:00`、`2026-11-18T03:00:00Z` 等写法统一规范为
  `YYYY-MM-DDTHH:MM` 存储，区间查询按字典序比较（规范后等价于时间序）。
- **数值展示**：整数值的浮点结果收敛为整数（如 `10.0 → 10`），除法保留小数；
  除数为 0、操作数缺值、依赖缺值都会给出可读原因。

## 已知限制

- 单进程 + SQLite，适合单站/小团队部署；多实例水平扩展需换外部数据库。
- 历史视角只显示该版本上传的批次（“当时的列名与当时的读数”），不把新批次映射进旧结构。
- 小时列按整点/分钟对齐，秒级或非 ISO 写法会被拒绝。
- 每个计算列只做一次四则运算，不支持括号、多步表达式或聚合；
  需要多步时请拆成多个计算列（依赖链会被正确版本化）。
- 文本列不参与四则运算；常量只接受有限数值。
- **批次视角与口径版本解耦**：`version_no` 决定看哪些批次、用哪套原始列名；
  `def_version_no` 决定用哪套计算口径。两者可独立选择（这正是“同一批读数按不同口径各算一遍”）。
  现行实现默认口径版本跟随批次视角，也可显式指定。
